# Trail 设计文档 v0.1

> 状态：草案（2026-11-01）
> 依据：[research/调研报告.md](../research/调研报告.md)、[research/调研报告-harness.md](../research/调研报告-harness.md)

## 1. 定位

**一个跨机器的开源 agent：在你的电脑和你的服务器之间干活，做完的每件事都拿得出证据，干活的每一步都看得见。**

| 层次 | 内容 | 现有项目的做法 | 我们的做法 |
|---|---|---|---|
| 产品定位 | **跨机器** | 一个会话绑定一个环境 | 一个会话挂多个工作区（本地 + 多台 SSH 服务器），每个工作区独立设置权限 |
| 核心机制 | **举证** | 提醒模型调用完成工具（Cline）；评审模型打分（OpenHands） | harness 强制要求：每条完成声明都要引用日志中的证据，校验不过就驳回 |
| 特色 | **透明** | 只有日志文件 | 内置检查器（Inspector）：看到每次请求的原文、token、缓存、花费；可从任意一步分叉重放 |

三者互相支撑：跨机器操作风险高，所以需要举证和按机器分级的权限；举证需要完整的事件日志，而这份日志正好也是透明检查器的数据来源。

### 非目标（第一阶段不做）
- 不做 IDE 插件
- 不做多 agent 团队协作
- 不做远端 daemon（SSH 只用库直连，即方案 A）
- 不做云端托管运行

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **工作区 Workspace** | 一台机器上的一个目录，分为 `local` 和 `ssh` 两种 |
| **会话 Session** | 一次连续的对话，**绑定一组工作区**，其中一个是主工作区 |
| **事件 Event** | 会话中发生的一切都是一条只追加的事件，**它是唯一的事实来源** |
| **资料库 Library** | 导入并建立索引的文档集合（开发文档、芯片手册等），与工作区平级，可挂到任意会话 |
| **证据 Evidence** | 由 harness 从工具执行事件中生成的、可校验的记录，模型无法伪造 |
| **声明 Claim** | 模型在完成任务时说的"我做到了 X"，必须引用证据 |
| **完成报告 Completion Report** | 所有声明及其证据和校验结果，展示给用户 |

## 3. 跨机器

### 3.1 会话与工作区

```ts
type Workspace =
  | { id: string; name: string; kind: "local"; path: string }
  | { id: string; name: string; kind: "ssh"; path: string;
      ssh: { host: string; port: number; username: string;
             auth: "password" | "key"; keyPath?: string;
             hostKeyFingerprint: string } }   // 密码和口令存入系统钥匙串

type SessionWorkspace = {
  workspaceId: string
  alias: string            // 给模型看的短名：local、staging、prod
  role?: string            // 可选说明："测试服务器，可随意部署"
  permission: PermissionLevel
}

type Session = { id; workspaces: SessionWorkspace[]; primary: string /* alias */ }
```

- 新建会话时选择主工作区（本地文件夹或 SSH）；会话中途可以**追加工作区**
- 常用工作区可以保存，下次一键选择

### 3.2 工具如何跨机器

- 所有工具都有可选参数 `workspace`（填别名），默认是主工作区
- 工具内部通过 `Operations` 接口执行（参考 pi），每个工作区对应一个实现：
  - `LocalOperations`：Node 的 `fs` 和 `child_process`
  - `SshOperations`：`ssh2` 长连接，文件走 SFTP，命令走 exec
- 跨机器搬运文件：`transfer(from, to, path)` 工具（M2）

### 3.3 按工作区分级的权限

```ts
type PermissionLevel =
  | "full"         // 读写和命令都不问
  | "ask-write"    // 读不问；写文件、执行命令要审批（默认）
  | "read-only"    // 只能读；写入一律拒绝；命令仅允许白名单（cat、ls、tail、grep、git status、systemctl status…）
  | "ask-all"      // 所有操作都要审批
```

- 默认值：本地为 `ask-write`；SSH 工作区为 `ask-write`；**名字或说明里含 prod、生产的，默认 `read-only`**
- 在等级之上叠加规则引擎（参考 OpenCode）：`(动作, 工作区, 资源通配符) → allow / ask / deny`，deny 优先
- 危险命令正则库（参考 Goose 的 `patterns.rs`）：`rm -rf /`、`mkfs`、`dd`、`shutdown`、`DROP DATABASE`…在任何等级下都要审批
- **来源加权**：从手机发起的会话，审批要求比同等级再严格一档

### 3.4 模型如何知道有哪些机器

system prompt 中有一个 `<workspaces>` 段：

```
<workspaces>
- local (primary): Windows 11, D:/proj/shop, 权限 ask-write, shell: bash(Git Bash)
- staging: Ubuntu 24.04, /srv/shop, 权限 full, 说明: 测试服务器，可随意部署
- prod: Ubuntu 24.04, /srv/shop, 权限 read-only, 说明: 生产环境，只能查看
</workspaces>
```

会话中途追加工作区时，**不重写 system prompt**，而是插入一条 system 增量消息（参考 pi 的 `declareToolChanges`），以保护 prompt cache。

## 4. 举证

### 4.1 证据从哪来

**证据只能由 harness 产生，模型不能直接写证据。** 每次工具执行结束，harness 自动生成一条证据记录：

```ts
type Evidence = {
  id: string                 // 如 "ev_12"，在工具结果末尾告诉模型
  sessionId: string
  workspace: string          // 别名
  kind: "exec" | "file_read" | "file_write" | "http" | "screenshot" | "doc"
  at: number                 // 时间戳，也是事件序号
  // kind = exec
  command?: string; exitCode?: number; durationMs?: number
  outputHash?: string; outputExcerpt?: string   // 输出全文另存，这里保留摘要
  // kind = file_write
  path?: string; diffHash?: string
  // kind = doc（见第 7 节，此时 workspace 为空）
  library?: string; doc?: string; page?: number; section?: string; quoteHash?: string
}
```

模型看到的工具结果形如：

```
...命令输出...
[evidence: ev_12 | staging | exit 0 | 3.2s]
```

### 4.2 完成工具

模型只能通过 `complete` 工具结束任务：

```ts
complete({
  summary: string,
  claims: Array<{
    text: string                           // "所有单元测试通过"
    kind: "tests_passed" | "command_succeeded" | "file_changed"
        | "service_healthy" | "observed" | "per_docs" | "unverified"
    evidence: string[]                     // ["ev_12"]
    workspace?: string
  }>
})
```

### 4.3 校验规则（M1 已实现全部 8 条）

| # | 规则 | 不通过时 |
|---|---|---|
| 1 | 引用的证据 id 必须存在，且属于本会话 | 驳回 |
| 2 | `tests_passed` / `command_succeeded` 必须引用 `exec` 证据，且 exitCode = 0 | 驳回 |
| 3 | **新鲜度**：`tests_passed` 的证据必须晚于该工作区**最后一次文件修改** | 驳回："改完代码后没有重新跑测试" |
| 4 | `file_changed` 必须引用对应路径的 `file_write` 证据 | 驳回 |
| 5 | 声明中的工作区必须与证据的工作区一致（不能拿 staging 的测试证明 prod） | 驳回 |
| 6 | 本会话有文件修改，但一条可验证的声明都没有 | 驳回，要求补充验证或明确标为 `unverified` |
| 7 | `unverified` 允许提交，但在报告中醒目标注"未验证" | 通过，带警告 |
| 8 | `per_docs`（依据文档）必须引用 `doc` 类型证据 | 驳回 |

- 驳回时，harness 把具体原因作为工具错误返回给模型，模型可以补跑测试后再次提交
- 连续驳回 3 次后，强制结束并生成报告，标注"举证失败"
- 校验器是纯函数：`validate(claims, eventLog) → Result`，方便单元测试

### 4.4 完成报告

```
✅ 任务完成：修复下单接口的并发 bug，并部署到 staging

  ✔ 所有单元测试通过           local    ev_31  npm test → exit 0（修改后 2 分钟运行）
  ✔ 已部署到 staging          staging  ev_35  systemctl restart shop → exit 0
  ✔ 服务健康                   staging  ev_36  curl /health → 200
  ⚠ 生产环境日志无相关报错（未验证）  prod   —   模型未提供证据

  改动文件：src/order.ts (+12 −3)   [查看 diff]
```

每条证据都可以点开，查看完整的命令输出和执行时间。

## 5. 透明（Inspector）

### 5.1 记录什么

每一次模型请求都记录为一组事件：
- `llm/request`：**实际发送的完整请求体**（去掉 API key）、模型、参数
- `llm/response`：完整响应（含思考内容、工具调用）
- `llm/usage`：input、cache_read、cache_write、output 四类 token，计算出的花费，延迟，首 token 时间

原则（来自 DeepSeek Harness）：**模型看到的，必须记在日志里**。任何一次请求都能从日志完整重建。

### 5.2 能看什么

| 视图 | 内容 |
|---|---|
| 时间线 | 每一轮：请求 → 回复 → 工具 → 证据，可展开 |
| 请求原文 | 某一轮实际发出的 JSON |
| 上下文构成 | system prompt、工具定义、历史消息、工具输出各占多少 token（堆叠条形图） |
| 缓存 | 每轮缓存命中率；**缓存失效时标出原因**（比如前缀从哪个位置开始变了） |
| 花费 | 按轮、按模型、按会话累计 |

### 5.3 分叉与重放

- 从任意一轮**分叉**：复制该点之前的事件，生成一个新会话（会话是一棵树，参考 pi）
- 分叉时可以更换模型、system prompt 或温度
- **对比视图**：两个分支并排，比较步数、花费、结果和证据
- 注意：重放时工具会**真实执行**。分叉时默认把工作区权限降为 `ask-all`，防止误操作

## 6. 上下文管理

### 6.1 原则：上下文是事件日志的视图

```
事件日志（只追加，永不删除，证据也在这里）
        │  View 投影（参考 OpenHands condenser）
        ▼
发给模型的上下文（有损视图）
```

- 压缩只改变视图，不删除事件，所以**压缩永远不会丢失证据**
- 校验器查询的是日志而不是上下文；模型只需要记住证据编号，早已被压缩掉的证据仍然可以在 `complete` 中引用

### 6.2 第 1 层：顺序与缓存

```
[身份与规则] [工具定义] [工作区列表] [项目说明] [历史消息 ……]
 ←──────────── 稳定前缀，命中缓存 ────────────→  ←─ 只在末尾追加 ─→
```

- **对话进行中不修改前缀，唯一的例外是压缩**（参考 Hermes、pi）
- 新增工作区、工具集变化：追加 system 增量消息
- 修改配置：下一个会话生效

### 6.3 第 2 层：源头控制体积

| 场景 | 做法 |
|---|---|
| 工具输出过长（> 2000 行或 50KB） | 给模型开头和结尾，全文存入 blob |
| 需要完整输出 | `read_output(evidenceId, offset, limit)`：**证据编号同时是取回全文的把手** |
| 大文件 | `read` 默认分段；超大文件先给结构概要 |
| grep、远程日志 | 默认限制条数，提示缩小范围 |

### 6.4 第 3 层：两级瘦身

| 触发 | 动作 | 是否调用模型 |
|---|---|---|
| 达到窗口的 60% | 裁剪旧工具输出，只保留一行 `[ev_12 · staging · exit 0 · 输出已省略]` | 否 |
| 达到窗口的 80% | 结构化摘要：较早历史 → 摘要，最近 N tokens 保留原文 | 是（用便宜模型） |
| 模型返回超长错误 | 硬重置：整体摘要后重试 | 是 |

- 两级都**批量执行**，避免每轮都让缓存失效
- 接近阈值时在后台预先计算摘要（参考 OpenCode）
- 压缩记为 `compaction/applied` 事件，Inspector 可以查看压缩前后的内容
- token 用量 = 上次响应中模型报告的实际值 + 之后新增内容的估算值
- 阈值根据模型配置中的上下文窗口计算，并预留输出空间

摘要模板：

```markdown
## 目标           （尽量保留用户原话）
## 约束与决定
## 各工作区状态    每台机器：改了哪些文件、分支与提交、部署了什么、重启了什么服务、只读查看过什么
## 证据账本        关键证据编号及其含义
## 待办与下一步
```

### 6.5 第 4 层：子 agent 隔离

- 会产生大量中间输出的探索任务（翻日志、查代码）交给子 agent，使用独立的上下文
- 主会话只收到结论和证据编号
- 子 agent 的证据写入同一份日志，主 agent 可以在 `complete` 中引用

### 6.6 第 5 层：可观察（Inspector）

- 每轮的上下文构成（system、工具、历史、工具输出各占多少）
- 每次压缩丢弃了什么、生成了什么摘要
- 缓存在哪一轮、前缀的哪个位置失效

## 7. 资料库（Library）

### 7.1 定位

| 资料类型 | 做法 |
|---|---|
| 之前项目的代码 | **不做 RAG**：作为只读工作区挂进会话，由 agent 用 grep / read 主动查找 |
| 开发文档、接口文档、芯片手册等 PDF / Markdown / Word | 导入**资料库**，解析后建立索引，由 agent 通过专用工具检索 |

- 资料库与工作区平级，一个资料库可以挂到多个会话（例如"STM32 资料库"挂到所有嵌入式项目）
- 解析结果和索引都存在本地，不上传

### 7.2 导入流水线

```
PDF / DOCX / MD / HTML
  → 解析（保留页码；表格保持表格结构；图片单独保存）
  → 按页切分为 Markdown，并抽取目录
  → 切块（以章节和页为边界，每块带 文档 · 页码 · 章节路径）
  → 建立索引（M1 版：SQLite FTS5 关键词索引）
  → 人工检查：可在界面中查看和修正某一页的解析结果（例如修正一张寄存器表）
```

- 解析器做成可插拔：默认 Docling；纯 Node 兜底（`pdfjs-dist`、`mammoth`）；以后可接 MinerU、Marker 等
- 解析器多为 Python 工具，以外部进程方式调用，不嵌入主程序
- 记录每个文档的哈希；文档更新时只重建变化的部分

### 7.3 检索：由 agent 主动发起

| 工具 | 作用 |
|---|---|
| `doc_search(query, library?, limit?)` | 混合检索，返回"文档 · 页码 · 章节 · 片段" |
| `doc_outline(doc)` | 返回目录，用于先定位章节 |
| `doc_read(doc, pages)` | 读取指定页的 Markdown |
| `doc_view_page(doc, page)` | 渲染该页为图片，交给支持视觉的模型（时序图、框图、引脚图） |

- **不自动注入**：不在每轮请求前塞入检索结果，以保护缓存，同时让检索过程在 Inspector 中可见
- system prompt 中仅列出已挂载的资料库名称和简介，放在稳定前缀里

### 7.4 混合检索

- **关键词优先**：寄存器名、函数名、地址（`GPIOA_MODER`、`HAL_UART_Transmit`、`0x40020000`）需要精确匹配，这是向量检索的弱项
  - 分词时把 `GPIOA_MODER` 同时切成整体和片段，并对十六进制地址做规范化
- **向量检索（后续加入）**：用于概念性问题（"怎么进入低功耗模式"），模型可以配置，也支持本地 embedding 模型
- 两路结果用 RRF（倒数排名融合）合并

### 7.5 与举证打通

查阅文档同样会生成证据：

```ts
// Evidence.kind 新增 "doc"
{ id: "ev_40", kind: "doc", library: "stm32", doc: "RM0090.pdf", page: 287,
  section: "8.4.1 GPIO port mode register", quoteHash: "…" }
```

- 声明新增类型 `per_docs`（"依据文档"），必须引用 `doc` 类型证据，否则驳回（校验规则 8）
- 完成报告中点开证据，可以直接看到原文那一页（文本或页面截图）

## 8. 架构

```
packages/
  protocol/     事件、命令、类型（所有端共享）
  llm/          模型适配：protocols/（anthropic、openai-compat）+ providers/（配置）
  agent/        无状态主循环（参考 pi agent-loop）
  workspace/    Workspace、Operations 接口，local / ssh 实现，连接池
  tools/        read / edit / write / bash / grep / glob / complete / transfer / read_output
  evidence/     证据生成、声明校验器、完成报告
  library/      资料库：导入流水线、解析器适配（外部进程）、FTS5 索引、doc_* 工具
  core/         会话、事件日志(SQLite)、权限引擎、压缩、配置、钥匙串
  inspector/    请求/用量统计、上下文构成分析、缓存诊断、分叉
  daemon/       WebSocket 服务；可选网关客户端（默认关闭）
  cli/          M1 的命令行入口
  desktop/      Electron（M4）
  gateway/      云端网关（M6）
```

依赖方向：`protocol` ← `llm` ← `agent` ← `core` ← `daemon` / `cli`；`workspace`、`tools`、`evidence`、`library` 被 `core` 组装。`agent` 不知道存储、证据和 UI 的存在，它们都通过回调接入。

### 事件类型（初版）

```
session/created  session/workspace-added
turn/start  turn/end
user/message  assistant/message
llm/request  llm/response  llm/usage
tool/call  tool/result  evidence/recorded
permission/asked  permission/answered
complete/submitted  complete/rejected  complete/accepted
compaction/applied  session/forked  session/library-attached
```

### 存储

- SQLite：`events(session_id, seq, type, at, payload_json)`，只追加
- 大块内容（完整命令输出、请求原文）存入 `blobs(hash, bytes)`，事件中只保存哈希
- 资料库：`library_docs`、`library_pages`、FTS5 虚拟表；页面图片与解析产物存在资料库目录下
- 优先使用 Node 内置的 `node:sqlite`（避免原生模块在 Windows 上的编译问题），必要时退回 `better-sqlite3`

## 9. 里程碑（按新定位重排）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1 内核** | llm（openai-compat + anthropic）、主循环、6 个工具 + `complete`、LocalOperations、事件日志、**证据与校验规则 1–4**、基础权限确认、CLI；`inspect` 命令可查看请求原文、token 和花费；**输出截断 + `read_output`、事件日志与 View 结构、按实际用量统计 token** | CLI 中完成"改 bug → 跑测试 → 提交带证据的完成报告"；改完不跑测试就提交，会被驳回 |
| **M2 跨机器** | SshOperations（ssh2，密码/密钥，host key 确认，钥匙串）、多工作区会话、按工作区分级权限、`transfer`、校验规则 5–7；**两级上下文瘦身 + 跨机器摘要模板 + 子 agent** | 一个会话中：本地改代码 → 传到 staging → 重启 → curl 验证；prod 上的写操作被拒绝 |

和之前的计划相比：**SSH 从 M3 提前到 M2**，因为它是产品定位；Inspector 拆成两部分，基础部分在 M1 就做（因为数据结构要从第一天起就记录完整）；**上下文压缩从末尾提前到 M1/M2**，因为跨机器任务步数多、输出大，到 M2 就会撑爆上下文；**新增 M3 资料库**，原 M3–M6 顺延一位。

- 远程机器仅支持 POSIX（Linux/macOS）；Windows 服务器作为 SSH 工作区暂不支持
